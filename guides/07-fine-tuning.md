# 🎛️ Build guide: fine-tuning or distillation you can justify

> **Time:** 2-4 weeks · **Difficulty:** 🟡 Intermediate · **Catalog entry:** [Fine-tuning & training](../catalog/fine-tuning.md)
> **Proves:** data hygiene, a fair prompt baseline, adapter training on a small budget, held-out evaluation, and a cost case for (or against) adapting a model.

Most fine-tuning projects on GitHub are a LoRA run, a falling loss curve and a few cherry-picked outputs. That shows you can run a notebook, not that the fine-tune was worth doing. This guide builds the version a reviewer can trust: one narrow task, a carefully prompted baseline, one adapted small model, and a table that says whether adaptation beat prompting on quality, speed or cost. If it didn't, a well-measured "prompting was enough" is still a strong result.

It fits a free or cheap GPU on purpose. Pick a model in the 1-4B range and train a LoRA or QLoRA adapter. You are not pretraining anything.

---

## 1. Scope

**Build:** one adapted small model for one narrow task. Pick one:

- **Support-intent classification:** map a customer message to one of 15-30 intents.
- **Schema-bound extraction:** turn a messy record (an invoice line, a job post) into fixed JSON fields.
- **Tool-call arguments:** given a request and a tool schema, produce valid arguments.

**Compare three systems on the same held-out cases:**

1. The untouched small model with a plain prompt.
2. The best prompted baseline you can build (few-shot examples, a schema, maybe a larger hosted model).
3. Your adapted small model: a LoRA adapter, or a student trained on a larger teacher's outputs (distillation).

**Leave out of the core:** pretraining, a general-purpose chat assistant, preference tuning or RL. Supervised fine-tuning is enough to make the case.

## 2. Architecture

```
owned / consented examples ─▶ dedupe ─▶ grouped train / dev / test split ─▶ prompt baseline
                                     └▶ optional teacher outputs ─▶ review + filter ─▶ training set
training set ─▶ LoRA / QLoRA adapter (pinned model + tokenizer revision) ─▶ held-out eval
            ─▶ merged or adapter deployment ─▶ speed + cost benchmark ─▶ model card
```

Design rules:

- **Record provenance for every example.** Where it came from, who may use it, and whether a teacher model wrote it. Check that the teacher's terms allow training on its outputs.
- **Split by group, not by row.** If 40 examples come from one template, one customer or one topic, keep them in the same split. Random splits leak near-copies into the test set.
- **Pin everything.** Base model revision, tokenizer revision, library versions, seed and training config go in the repo.
- **Use the same matching rules for every row.** Freeze the scorer before training, so you can't tune the metric to the model.
- **Distillation is a specific claim.** Call it distillation only when a student learns from a teacher's outputs. A plain fine-tune on human labels is a fine-tune.

## 3. Milestones

| Week | Ship | Done when |
|---|---|---|
| 1 | Task definition, provenance log, grouped train / dev / test split, frozen scorer, prompt baselines | `make eval` scores both baselines on the held-out set |
| 2 | One reproducible adapter run from a config file | A second run from a clean checkout lands within noise of the first |
| 3 | Teacher-data filtering or one training ablation (data size, rank, epochs), slice evaluation | You have a baseline-vs-adapted table with hard slices broken out |
| 4 | Deployment speed benchmark, training-cost ledger, model card, failure review | A stranger can retrain, re-evaluate and reproduce your table |

**Two weeks only?** Stop after week 2 with one clean baseline-vs-adapter comparison on held-out data.

## 4. The dataset

The dataset decides the result more than the training settings. Build it before you train anything.

- **1,000-5,000 training examples** is plenty for a narrow task on a small model. Short inputs keep memory and cost low.
- **300-500 held-out test cases**, labelled by you or reviewed by you, never generated by the teacher you're distilling from.
- **Hard slices:** an unseen template, an unseen customer or topic, rare labels, messy inputs. Report each slice separately.
- **Dedupe across splits** with exact and near-duplicate checks. Log how many you removed.
- **If a teacher writes training data,** review a sample by hand, filter bad outputs with your scorer, and log the rejection rate.

## 5. What to measure

| Metric | How to compute | Baseline (prompted) | Adapted model |
|---|---|---|---|
| Task quality | Exact-match accuracy or field-level F1 using the frozen matching rules | | |
| Format validity | Schema-valid outputs ÷ all attempts | | |
| Hard-slice quality | The same task metric on each unseen template / customer / topic group | | |
| Regression rate | Held-out cases the baseline passed that now fail ÷ baseline-passing cases | | |
| Inference efficiency | p50 / p95 latency, tokens, and cost per correct output on the same hardware | | |
| Adaptation cost | Teacher generation + review time + all training runs + experiment compute | n/a | |

Notes that make the table credible:

- **Training loss is not a result.** Only held-out task metrics go in the table.
- **Report denominators** ("412 of 450 valid JSON"), and run the eval more than once if decoding is sampled.
- **Compare like with like.** Same test cases, same output length limits, same hardware for speed.
- **Break-even:** `adaptation cost ÷ (baseline cost per correct output − adapted cost per correct output)` tells you how many outputs it takes to pay back the training spend. If the denominator is zero or negative, there is no cost case, only a quality one (or none).

## 6. Compute and cost

**What fits a free or cheap GPU.** QLoRA trains a small adapter on top of a 4-bit base model; the QLoRA paper fine-tunes a 65B model on a single 48GB GPU ([📄 QLoRA](https://arxiv.org/abs/2305.14314)). Your 1-4B model needs far less. Unsloth's requirements page lists 3.5 GB as the minimum VRAM for QLoRA on a 3B model and 8 GB for 16-bit LoRA, and calls these absolute minimums ([📘 Unsloth requirements](https://docs.unsloth.ai/get-started/beginner-start-here/unsloth-requirements)).

**A cheap path:**

- Start in a free notebook. Colab offers free GPU access, but its FAQ says resources are not guaranteed and usage limits fluctuate ([📘 Colab FAQ](https://research.google.com/colaboratory/faq.html)). Save checkpoints often and keep runs short.
- Use Unsloth's free notebooks or TRL's `SFTTrainer` with a PEFT LoRA config. Keep batch size small and sequences short.
- Pick a base model whose licence you can live with: [Qwen3-1.7B](https://huggingface.co/Qwen/Qwen3-1.7B) and [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) are Apache-2.0; [Llama 3.2 1B Instruct](https://huggingface.co/meta-llama/Llama-3.2-1B-Instruct) is under the Llama 3.2 Community License and [Gemma 3 1B](https://huggingface.co/google/gemma-3-1b-it) under the [Gemma Terms of Use](https://ai.google.dev/gemma/terms); both are gated on Hugging Face.
- If you need a steadier machine for the final runs, rent one GPU by the hour and log the billed hours.

**Log for every run, including failed ones:** GPU type and count, billed hours, peak memory, sequence lengths, precision, batch settings and teacher API spend. A free notebook is not zero cost; price what the same hours would cost to rent, and date the price. Measure deployment speed separately from training speed.

## 7. Common mistakes

- Leakage through duplicate templates or near-identical examples across splits.
- Reporting training loss or a few hand-picked outputs instead of a held-out table.
- No prompted baseline, so nobody knows whether fine-tuning was needed.
- Calling any fine-tune "distillation".
- Testing on teacher-written labels, so the student is graded on copying the teacher.
- Ignoring data rights, or assuming the training library's licence covers the model weights or the dataset.

## 8. Stretch goals

- **Human vs teacher data:** compare a small hand-curated set against a larger teacher-generated one at equal training cost.
- **On-policy distillation:** try TRL's Distillation Trainer, which trains the student on its own generated sequences with teacher feedback ([📄 GKD paper](https://arxiv.org/abs/2306.13649)).
- **Quantize the result:** check whether the task gain survives 4-bit or GGUF export.
- **Serve it:** put the adapter behind the serving setup from [guide 8](08-llm-serving.md) and measure cost per correct output under load.
